## The problem: metadata that arrives before you do

A photographer shoots 300 images and fills in the caption, creator and copyright in their editing software. They hand the files to your brand team. Does anyone have to type that again?

No, because the information is already **inside the files**. Understanding how it gets out, and what happens when you change it, is the difference between a DAM that saves effort and one that quietly contradicts its own files.

## Three standards in one file

- **EXIF** is written by cameras: model, lens, exposure, date and GPS position.
- **IPTC** is written by people: headline, caption, creator, copyright, keywords.
- **XMP** is the modern container. It is XML stored inside the file, grouped by **namespaces** so properties do not clash. `dc:title` belongs to Dublin Core, `xmp:CreateDate` to the XMP basic schema, `photoshop:Credit` to Photoshop's.

Adobe's documentation notes that legacy EXIF, ID3 and Microsoft Office metadata is translated into XMP, so AEM works with one model.

## What AEM does on upload

When you upload a file, AEM Assets reads the embedded metadata and saves it on the asset's `jcr:content/metadata` node. This is **extraction**. Those values then show up in the Properties page, in search and in your schema fields, wherever a field is mapped to the same property.

That is why mapping matters. A schema field mapped to `./jcr:content/metadata/dc:title` shows whatever extraction found there. If a field is mapped to a property no file ever fills, it starts empty and stays empty until a person fills it.

```text
Uploaded file (embedded)       AEM metadata node
dc:title   = "Red trainer"  -> jcr:content/metadata/dc:title
dc:rights  = "(c) Acme 2026" -> jcr:content/metadata/dc:rights
exif:Model = "X-T5"         -> jcr:content/metadata/tiff:Model
```

## Which value wins?

Adobe's pages explain namespaces but do not give a single rule for conflicts, so treat it as a process question. Extraction runs at upload and processing. A person's edit in AEM changes the metadata node. If the file is re-processed or re-uploaded, embedded values can arrive again. So:

1. Decide which fields are **owned by the supplier** (copyright, creator) and which are **owned by your team** (campaign, usage region).
2. Keep your own fields in your own namespace, so extraction never touches them.
3. Test with one file before a mass upload.

## Writeback: sending edits back into the file

By default, edits in AEM stay in the repository. The binary you download keeps its old embedded metadata. **XMP writeback** closes that gap. On Cloud Service the documented route is the **DAM Metadata Writeback** workflow. It is not enabled by default. You can turn on its launcher under **Tools, Workflow, Launchers**, run the workflow manually on an asset, or add it to a post-processing profile.

Points from the documentation worth remembering:

- Edits are saved on the metadata node first, then propagated to the original's renditions, either all of them or selected ones.
- Only properties in the `jcr` namespace are written back.
- On assets in a multi-site setup, writeback breaks inheritance.
- Bulk writeback is resource-intensive, so schedule large jobs for quiet periods.

Cloud Service also changes how processing is organised, which is the subject of level 3. Check Experience League for the current state of writeback options before you design around it.

<details markdown="1">
<summary>Predict first, then reveal: why enable writeback at all?</summary>

Because assets leave the DAM. A product image downloaded by a reseller, or attached to an email, no longer has your repository to explain it. If the title, copyright and keywords are embedded in the file, they travel with it. The price is extra processing and a rule about who may edit what, which is why many teams switch it on only for the asset types where it matters.
