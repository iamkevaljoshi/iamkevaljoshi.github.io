## Why the design changed

Picture a single post office with one clerk. Every parcel must be carried in, opened, measured, repackaged and shelved by that clerk. When Black Friday arrives, the queue is out of the door.

That was the shape of AEM 6.5 Assets (legacy). Uploaded bytes streamed through the AEM server, were stored in the content repository's storage, and a workflow called **DAM Update Asset** created renditions and extracted metadata on the same JVM. Large uploads and big video jobs competed with authors for the same CPU and memory.

AEM Assets as a Cloud Service splits the job into specialist stations.

## The four moving parts

**1. Binaries in cloud storage.** The file bytes live in cloud blob storage. The repository keeps metadata and references. This is the same idea as the one explained in the blog post on content outside the JCR: keep big, immutable blobs out of the structured store.

**2. Direct binary upload.** The client asks AEM to start an upload, receives pre-signed storage URLs, sends file parts straight to storage, then tells AEM it is complete. AEM never carries the bytes. Downloads of originals can likewise go straight to storage.

**3. Asset microservices.** Once an upload completes, AEM sends a processing request. Services built on Adobe **Asset Compute** read the original from storage, create the renditions defined by the folder's **processing profile**, extract metadata and text for search, and report back. Adobe operates and scales them. Where defaults are not enough, you can add custom processing (level 3).

**4. Author tier and delivery tier.** Authors and asset managers work on the author tier. Visitors are served from a delivery tier made of publish, the CDN and, where licensed, Dynamic Media. Level 4 compares these options.

## One upload, end to end

```text
Browser / tool
   | 1. "start upload" (small request)
   v
AEM author  --- returns pre-signed URLs --->  Browser
   ^                                             | 2. send file parts
   | 4. metadata + renditions saved              v
   |                                    Cloud blob storage
   |                                             | 3. "complete" -> processing request
   +------------------ Asset microservices <-----+
                       (read original, write renditions)
```

Notice what travels where: only small control messages touch the author server. The heavy bytes go from client to storage to microservices.

## What this changes for you

- **Ingestion scales with load** instead of with the size of your author instance.
- **Processing is configured, not scripted.** You choose a processing profile per folder rather than editing the update workflow. Some post-processing workflows still exist for custom needs.
- **Failures have new places to look:** the asset's processing status, the profile and, for custom code, Asset Compute logs.
- **Design decisions matter earlier.** Because profiles attach to folders, your folder structure (next lesson) becomes a processing and governance decision too.

Details such as exact supported formats and defaults change over time, so confirm them on Experience League when you design.

<details markdown="1">
<summary>Predict first, then reveal: what happens if storage is reachable but the microservices are slow?</summary>

The upload still succeeds, because the bytes are already safe in storage and the asset exists. What lags is the generated renditions and extracted metadata, so thumbnails or search results may appear a little later. Separating storage from processing is what makes this graceful.
